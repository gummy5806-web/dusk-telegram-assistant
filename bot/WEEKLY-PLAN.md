# План недели — как зафиксировать и почему это вручную

Коротко: **процент выполнения считается по сохранённому плану конкретных
карточек, а не по датам.** Пока план не зафиксирован (или он неполный/чужой
недели), `Статус.md` пишет «не зафиксирован» с причиной и не показывает ни 0%,
ни выдуманные сто.

## Зачем

Раньше показатель собирался так: «все карточки, у которых `scheduled` не старше
семи дней». Отсюда три проблемы:

1. верхней границы не было — карточка с планом на 2030 год попадала в текущую неделю;
2. перенос даты карточки менял процент, хотя обязательства не менялись;
3. набор, собранный автоматически в момент расчёта, назывался «планом», хотя
   владелец его не согласовывал.

## Как зафиксировать (единственный способ — вручную)

```bash
cd "<валт>"
python3 bot/weekly_plan.py freeze "разобраться с парсером" "написать парсер новостей"
```

Имена — это имена файлов задач в `TaskNotes/Tasks` (если имя не совпало, берётся
однозначный `title`). Команда создаёт `Учеба/план недели.md` на текущую неделю
(понедельник–воскресенье, `Asia/Almaty`) и запоминает момент фиксации.

Посмотреть состояние:

```bash
python3 bot/weekly_plan.py show
```

Пример, когда план есть и одна карточка была заменена:

```
План недели 2026-10-05 — 2026-10-11: 0/2 = 0%
  ❓ первое — карточка заменена новой с тем же названием
  ⬜ второе
  ❓ не найдено: 1 (в знаменателе остаются)
```

## Идентичность обязательства

Устойчивая идентичность — поле **`duskTaskId`** в шапке карточки. Его записывает
сам `freeze`, и только тем карточкам, которые пользователь назвал вручную: если
ID уже есть, он сохраняется, повторная фиксация его не меняет. Массовой миграции
нет — остальные карточки не трогаются.

Так сделано потому, что имя файла и `created` идентичностью не являются: карточку
можно переименовать, а на её место положить другую с тем же именем и той же
минутой создания. По ID такого не происходит.

| Что произошло | Что покажет отчёт |
|---|---|
| Карточку перенесли на другую дату | ничего не меняется (план не про даты) |
| Переименовали файл и/или заголовок | обязательство найдено по ID |
| Удалили и создали новую с тем же названием | `❓ карточка с зафиксированным ID не найдена` — выполнение **не** засчитывается |
| Две карточки с одинаковым ID | `⚠️ неоднозначность` — случайную не выбираем |
| Карточка удалена | `❓` (в знаменателе остаётся) |
| Закрытие датой из будущего | `⏳` — выполнением не считается |
| **План без ID** (старый строковый формат) | `❔ связь не подтверждена` — обязательство в знаменателе, выполнение **не** засчитывается |

Последний пункт — осознанное ужесточение: пока связь не подтверждена устойчивым
ID, система не начисляет выполнение и не привязывает обязательство к новой
одноимённой карточке. Чтобы засчитать старый план, зафиксируйте его заново:
`freeze` проставит ID карточкам и перезапишет записи.

## Формат файла

```markdown
---
type: weekly_plan
timezone: Asia/Almaty
week_start: 2026-10-05
week_end: 2026-10-11
frozen: 2026-10-05T09:14:00+05:00
tasks:
  - {"title": "разобраться с парсером", "stem": "разобраться с парсером", "created": "2026-10-04T18:24", "id": "6f1c2f0e-6a7b-4f5a-9c1d-2b3e4f5a6b7c"}
---
```

Каждый элемент списка `tasks` — **одна строка** JSON-объекта: многострочная
запись текущим разборщиком не читается.

Файл можно править руками, но поле `id` — это и есть идентичность обязательства:
без него запись остаётся в знаменателе и не засчитывается как выполненная. Формат
со строками (`- "название"`) читается ради совместимости: план не ломается, но
выполнение по таким записям не начисляется.

## Что проверяется при чтении

План считается зафиксированным только если:

* `type: weekly_plan`, `timezone: Asia/Almaty`;
* `week_start`/`week_end` — реальные даты, понедельник и воскресенье одной недели;
* `frozen` — момент времени **с часовым поясом**;
* `tasks` — непустой список записей, у каждой есть название.

Иначе метрика сообщает причину («нужна зона Asia/Almaty…», «границы недели не
понедельник–воскресенье», «поле tasks должно быть непустым списком» и т. д.) и
**не** переписывает файл: read-only расчёт план не создаёт и не правит.

## Какие конспекты считаются своими

Конспект, созданный Dusk, помечен в шапке `generator: dusk` — это **единственное**
основание считать файл своим. Обычная подпись «Источник» владением не является:
её может поставить кто угодно, и ручная заметка с ней не должна подменять наш
результат. Заметки, сделанные до появления маркера, автоматически не размечаются:
они остаются как есть, а разбор выходит отдельным файлом. Поэтому:

* ручная заметка с тем же `reference` **не перезаписывается** — разбор выходит
  отдельным файлом под свободным именем;
* **существующие файлы не изменяются вообще.** Недописанный черновик, ручная
  заметка и старый конспект сохраняются дословно — вместе с повторами, пустыми
  строками и порядком; завершённый результат публикуется рядом под свободным
  именем. Построчное слияние убрано: оно теряло строки и повторы;
* повтор уже разобранной ссылки находит завершённый результат и не создаёт дубль.

## Правила

* **Обе границы обязательны.** Неделя — закрытый интервал `week_start…week_end`.
* **Фактические закрытия не позже сегодня.** Дата закрытия из будущего в отчёт
  не попадает, даже если она внутри текущей недели.
* **Пропавшая карточка не улучшает процент** — она остаётся в знаменателе.
* **Неоднозначность показывается явно:** несколько карточек с одним ID или
  запись без ID помечаются, а не «выполнено».
* **Метаданные — только из шапки.** Пример `completedDate:` или `status:` в
  тексте заметки (включая code fence) метаданными не считается.
* **Даты строгие.** `completedDate` — полная ISO-дата или полный ISO-timestamp;
  timestamp приводится к Asia/Almaty. `2026-10-06invalid` — не дата.

## Что не входит

* Автоматическое формирование плана за владельца.
* Распределённая гарантия через Git: если Mac и VPS правят файл одновременно,
  побеждает последний коммит. См. отчёт этапа 1.
